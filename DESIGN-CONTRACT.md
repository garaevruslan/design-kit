# DESIGN-CONTRACT

Это активный проектный контракт комплекта **design-kit**: генерация дизайн-систем и
Figma-макетов сайтов на основе референсов. Агент, работающий в проекте с этим файлом,
обязан следовать контракту. Контракт важнее общих привычек модели: если внутренняя
интуиция агента противоречит правилу — действует правило.

Спецификация комплекта: `thoughts/shared/specs/2026-07-05-figma-design-kit.md`
(в репо-источнике; в копии проекта может отсутствовать — контракт самодостаточен).

## Обязательный preflight

До любой работы над дизайном, извлечением, библиотекой или макетами:

1. Прочитать `docs/workflow.md` — определить текущую фазу и её входы/выходы.
2. Прочитать доки, назначенные фазе в таблице маршрутизации.
3. Убедиться, что предыдущий гейт пройден (см. «Гейты»). Не пройден — работа не начинается.
4. Записать в `project/worklog.md` verification note: фаза, план проверок, что пропускается и почему.

## Карта фаз

```
Фаза 0. Инициализация        входы: референсы, бриф/контент → project/inputs.md
Фаза 1. Reference Study      извлечение данных → reference-study.md + reference-inventory.md
Фаза 2. Дизайн-система       tokens.json + design-system.md + specimen в Figma
        ── ГЕЙТ 1: человек утверждает дизайн-систему ──
Фаза 3. Контент и структура  content-doc.md (принять готовый или сгенерировать из брифа)
        ── ГЕЙТ 2: человек утверждает структуру и контент ──
Фаза 4. Библиотека в Figma   variables → компоненты (desktop + mobile)
        ── ГЕЙТ 3: человек утверждает библиотеку ──
Фаза 5. Сборка макетов       страницы из инстансов; композиция по каскаду; motion-spec.md
Фаза 6. Верификация          аудит → скриншот-сверка → анти-паттерны → отчёт расхождений
        ── ГЕЙТ 4: финальная приёмка человеком ──
Фаза 7. Harvest              кандидаты в накопительную библиотеку → утверждение → library/
```

Для лендинга в 1 страницу гейты 2 и 3 можно объединить с гейтом 1 (одно утверждение
пакета «система + структура + план библиотеки»). Решение фиксируется в worklog.

## Правила (rule ID)

Каждое правило имеет ID. В worklog решения ссылаются на ID применённых правил.

### `reference-source-of-truth`
Визуальные значения (цвет, шрифт, размер, отступ, радиус, тень) берутся только из
извлечённых данных референса или из утверждённых шкал tokens.json. Скриншот референса —
эталон для QA-сверки, а не источник, из которого «на глаз» снимаются значения при живом
сайте. Придумывать значения из памяти модели запрещено.

### `tokens-before-pixels`
До прохождения гейта 1 (утверждённый tokens.json) запрещено создавать библиотеку,
компоненты и макеты — в Figma или HTML. Сначала система — потом пиксели.
Единственное разрешённое (и ОБЯЗАТЕЛЬНОЕ) исключение — **specimen**: образец
системы (палитра, шкала типографики, кнопки/бейджи, образец тёмной секции),
собранный на variables/свойствах из tokens.json — в форме своего пути
(см. «Пути без Figma MCP»: Figma-страница / .pen-фрейм / specimen-страница
в браузере). Человек не утверждает дизайн-систему по текстовому описанию —
гейт 1 предъявляется только вместе со specimen (урок первого прогона).

### `no-detached-values`
В Figma-библиотеке и макетах нет «отвязанных» значений: каждый цвет, шрифт, отступ,
радиус привязан к variable/стилю из tokens.json. Исключения (например, уникальная
декоративная графика) фиксируются в worklog поимённо. Проверяется аудитом фазы 6.

### `instances-only`
Макеты (фаза 5) собираются только из инстансов компонентов библиотеки. Понадобился
новый паттерн — сначала компонент в библиотеку (мини-возврат в фазу 4), потом инстанс.
Рисовать «одноразовые» элементы прямо в макете запрещено.

### `composition-cascade`
Композиция каждой секции выбирается по каскаду приоритетов:
1. В референсе есть аналогичная секция → берём её композицию из reference-inventory.
2. Нет в референсе → берём скелет из `library/skeletons/`.
3. Нет нигде → модель компонует сама в рамках системы и помечает секцию
   `composition: invented` в worklog. Такие секции человек проверяет в первую очередь.
Источник композиции каждой секции фиксируется в worklog.

### `manual-edits-respected`
Перед любой регенерацией/правкой существующего Figma-файла агент снимает дифф текущего
состояния файла против данных проекта (tokens.json, content-doc, inventory). Найденные
ручные правки либо втягиваются в данные (обновить данные, затем регенерировать), либо
явно перезаписываются с согласия человека. Молчаливая перезапись ручных правок запрещена.
Исключение: файл-проекция накопительной библиотеки (см. `library/README.md`) —
он всегда перезаписывается целиком из данных.

### `vision-values-snapped`
Значения, извлечённые vision-путём (со скриншотов), обязаны: (а) приводиться к
консистентным шкалам, а не переноситься сырыми; (б) иметь пометку уверенности
(high/medium/low); (в) уступать CSS-пути, если живой аналог доступен.

### `gates-are-blocking`
Гейт — блокирующая остановка. Агент предъявляет артефакты фазы, задаёт вопрос на
утверждение и не начинает следующую фазу до явного «утверждаю» от человека.
«Молчание» или «наверное ок» — не утверждение.

### `worklog-required`
`project/worklog.md` ведётся по ходу работы (decision trail: решение, источник,
применённые правила, отвергнутые альтернативы, проверки). Сдача фазы без записей
в worklog не принимается. Формат — `templates/worklog.md`.

### `harvest-is-curated`
В `library/` попадают только паттерны, явно утверждённые человеком на фазе 7.
Автоматическое самопополнение библиотеки запрещено. Два режима записи:
**владелец комплекта** пишет в `library/` основного репозитория напрямую;
**ученик/контрибьютор** оформляет кандидатов pull request'ом по `CONTRIBUTING.md`
(ветка `harvest/<имя-проекта>`), решение о мерже — за куратором комплекта.

### `font-license-check`
Шрифт референса проверяется до включения в tokens.json по ТРЁМ осям:
(1) лицензия — коммерческий без подтверждённой лицензии → свободный аналог;
(2) глифовое покрытие под язык КОНТЕНТА проекта, а не референса — референс может
быть Latin-only при русском контенте (Figma молча подставит фолбэк, это ловится
только рендером — проверять через listAvailableFontsAsync + пробный рендер);
(3) доступность в шрифтовой библиотеке Figma. Любая замена и её мотивировка
фиксируются в design-system.md.

### `placeholders-for-assets`
Изображения (фото, иллюстрации) в v1 — аккуратные плейсхолдеры; для каждого в worklog
описывается желаемый ассет (сюжет, стиль, формат). Генерация/подбор — отдельный шаг
вне контракта v1. Иконки под это правило НЕ подпадают — они извлекаются как вектор
(`icons-from-collection`), плейсхолдер иконки — только при отсутствии аналога в коллекции.

### `icons-from-collection`
Все иконки проекта — из одной коллекции (Reicon) через `scripts/fetch-icons.mjs`.
Ручная отрисовка иконок и смешивание коллекций запрещены. Нет точной иконки — ближайший
семантический аналог из той же коллекции; совсем нет — плейсхолдер + пометка человеку
на гейте 3. См. `docs/icons.md`.

### `icon-single-weight`
Один вес иконок (outline или filled) на весь проект. Вес выбирается по стилю иконок
референса, зафиксированному в фазе 1 (не по вкусу модели), и указывается в design-system.md.

### `icon-color-from-roles`
Цвет иконок задаётся только через роли токенов (`color.text`, `color.text-muted`,
`color.accent`), никогда прямым hex. SVG используют `currentColor` и наследуют цвет от роли.

### `motion-spec-required`
`project/motion-spec.md` — обязательный артефакт фазы 5, в том числе для статического
проекта (тогда одна строка «статический проект, причина …»). Пустой файл без причины =
фаза не сдана. Формат — `templates/motion-spec.md`, правила — `docs/motion.md`.

### `motion-motivated`
Каждая анимация в motion-spec отвечает, что она коммуницирует: иерархия / storytelling /
feedback / изменение состояния. «Красиво» — не мотивация. Немотивированная анимация не
проходит гейт 4.

### `motion-observed-classified`
Наблюдение за референсом (программный скролл) даёт только КЛАССИФИКАЦИЮ паттерна
(sticky-stack / horizontal-pan / …), не точные значения. Длительности и easing берутся
из CSSOM референса (детерминированное чтение, уровень A) или из дефолтов каталога
`library/motion/`, но не выдумываются из наблюдения. См. `docs/motion.md` (уровни A/B/C).

### `motion-reduced`
HTML-путь обязан уважать `prefers-reduced-motion`: всё сложнее hover схлопывается в
статику. Проверяется на гейте 4.

### `no-invented-ai-tells`
Изобретённые секции (`composition-cascade`, ступень 3) и сгенерированный из брифа контент
проходят чек-лист `docs/anti-patterns.md`. Паттерн, унаследованный из референса, легален
(`reference-source-of-truth`) — в отчёте максимум warning, не блокировка гейта.

## Верификационные tier'ы

Перед каждой правкой классифицировать изменение по blast radius:

| Tier | Когда | Обязательные проверки |
| --- | --- | --- |
| Tier 0 — тексты/копия | Меняется контент в макете без структуры и стилей. | Визуальная проверка затронутых фреймов (влезание текста). |
| Tier 1 — один компонент | Правка одного компонента/варианта без изменения токенов. | Скриншот компонента + точечная проверка макетов, где он используется. |
| Tier 2 — состав макета | Добавление/удаление секций, перестановка, новые инстансы. | Аудит привязок затронутых страниц + скриншот-сверка изменённых секций. |
| Tier 3 — токены/система | Изменение tokens.json, шкал, ролей, переменных. | Полный аудит фазы 6 по всем страницам: токены инвалидируют всё. Регенерация через `manual-edits-respected`. |
| Tier 4 — сдача | Первая поставка или пересдача после крупных правок. | Полная фаза 6 (все три слоя) + актуальный worklog + verification-report. |

Сомневаешься между tier'ами — бери на один выше.

## Пути без Figma MCP

Оператор без доступа к Figma MCP выполняет фазы 0–3 полностью (они не требуют
Figma), затем фазы 4–6 по одному из двух путей. Все правила контракта действуют
без ослаблений; артефакты проекта идентичны. Режим фиксируется в шапке worklog:
`figma-mcp` | `pencil` | `fallback-html`.

- **`pencil`** — библиотека и макеты в .pen-файле (Pencil + Pencil MCP),
  по `docs/pencil-path.md`. Полноценная дизайн-канва; deliverable — .pen в
  `project/` (открытый JSON, git) + export_html/PNG.
- **`fallback-html`** — HTML-прототип на токенах с проверкой в браузере,
  по `docs/fallback-html.md`. Итог — полуфабрикат-спецификация; проекция в
  Figma выполняется оператором с доступом.

**Specimen гейта 1 обязателен на любом пути**; форма зависит от пути:

| Путь | Specimen гейта 1 |
| --- | --- |
| `figma-mcp` | страница «01 Specimen» в Figma (figma-library-rules.md §specimen) |
| `pencil` | фрейм «00 Specimen» в .pen + скриншот get_screenshot (pencil-path.md) |
| `fallback-html` | specimen-страница на tokens.css в браузере + скриншоты обеих ширин (fallback-html.md) |

Содержимое одинаково: палитра-свотчи, шкала типографики с образцами на языке
контента, кнопки/бейджи/инпуты, образец тёмной секции. Это единственный способ
поймать отсутствие глифов и инверсию тем до утверждения системы.

## Что считается завершённой поставкой

- Все гейты пройдены и зафиксированы в worklog (кто и когда утвердил).
- Аудит фазы 6 чист или все исключения поимённо утверждены.
- Каждая секция макета имеет источник композиции; `invented`-секции просмотрены человеком.
- Библиотека: каждый компонент привязан к variables, имеет мобильную версию/поведение.
- Иконки — из одной коллекции, один вес, цвет через роли (или плейсхолдеры утверждены).
- motion-spec.md сдан (или явно зафиксировано, что проект статический).
- Verification-report сдан вместе с макетами.
- Фаза 7 (harvest) предложена человеку — даже если кандидатов нет, это зафиксировано.
