# Правила фазы 4: библиотека в Figma

Этот док регламентирует сборку Figma-библиотеки: variables из tokens.json, затем
компоненты. Читается перед началом фазы 4 (см. `docs/workflow.md`). Выход фазы —
библиотека, предъявляемая на гейт 3. Применяемые правила контракта:
`no-detached-values`, `tokens-before-pixels`, `worklog-required`, `instances-only`
(готовит почву для фазы 5).

## Предусловия

1. Гейт 2 пройден и зафиксирован в worklog (`gates-are-blocking`).
2. tokens.json утверждён (гейт 1) и валиден по `scripts/validate-tokens.mjs`.
3. content-doc.md и reference-inventory.md доступны — из них выводится состав библиотеки.
4. **Перед первым вызовом `use_figma` обязательно загрузить скиллы `figma-use` и
   `figma-generate-library`.** Вызов `use_figma` без загруженных скиллов запрещён —
   это источник трудноотлаживаемых ошибок.

## План библиотеки — ДО сборки

До первого создания чего-либо в Figma в `project/worklog.md` записывается план библиотеки:

- полный список компонентов к сборке;
- для каждого — из какого паттерна reference-inventory он выводится
  (или пометка, что компонент базовый и следует из content-doc);
- для каждого — планируемые варианты (состояния, размеры) и стратегия адаптива
  (см. «Десктоп + мобайл» ниже).

Компонент, не попавший в план, не собирается. Понадобился новый по ходу — сначала
дополнение плана в worklog (decision-trail запись), потом сборка.

## Порядок сборки

Строго последовательно; следующий шаг не начинается, пока предыдущий не завершён.

### Шаг 1. Variables из tokens.json

Коллекции variables создаются 1:1 из tokens.json. Именование переменных — 1:1 с
ключами tokens.json (английские, без переименований «для красоты»):

| Коллекция | Источник в tokens.json | Режимы |
| --- | --- | --- |
| `color` | цветовые роли | `light` / `dark` — если в tokens.json есть обе темы; иначе один режим |
| `typography` | type scale (size, line-height, weight, family) | один |
| `spacing` | spacing scale | один |
| `radius` | радиусы | один |
| `shadows` | тени (как стили эффектов + числовые variables при необходимости) | один |

Правила:

- Ни одной variable, отсутствующей в tokens.json. Ни одного ключа tokens.json без
  variable (кроме служебных — например брейкпоинты, которые фиксируются как
  ширины фреймов, а не variables).
- Расхождение имён «ключ tokens.json ↔ имя variable» — дефект, блокирующий шаг 2.
- Тени, которые Figma не позволяет привязать к variable напрямую, оформляются
  effect-стилями с именами 1:1 из tokens.json.

### Шаг 2. Базовые компоненты

Атомарные компоненты, из которых состоят секции: Button, Input, Card, Nav, Footer,
Badge, Link и т.п. Состав — по reference-inventory (что реально встречается в
референсе) плюс то, что требует content-doc. Не собирать «стандартный UI-kit на
всякий случай»: только компоненты из плана.

### Шаг 3. Секционные компоненты

Компоненты уровня секций (Hero, Features, Pricing, CTA, FAQ...) — собираются из
инстансов базовых компонентов шага 2, а не из сырых фреймов, где это возможно.
Каждый секционный компонент маппится на паттерн reference-inventory или скелет
`library/skeletons/` (источник фиксируется в worklog по `composition-cascade`).

## Требования к каждому компоненту

### Варианты состояний

Каждый интерактивный компонент имеет варианты состояний там, где они применимы:
`state=default|hover|disabled` (для полей ввода дополнительно `focus`, `error` —
если референс/контент их требует). Неинтерактивным компонентам (Card без ссылки,
Footer) состояния не нужны — не плодить пустые варианты.

### Размерные варианты

Добавляются при необходимости: если референс или content-doc используют компонент
в нескольких размерах — prop `size=sm|md|lg` (значения из шкал tokens.json).
Один размер в проекте — один вариант без prop `size`.

### Десктоп + мобайл

Каждый компонент обязан иметь мобильную версию или мобильное поведение. Два способа,
критерий выбора:

| Способ | Когда выбирать |
| --- | --- |
| Авто-поведение через autolayout (wrap, fill, min/max width) | Мобильная версия — то же расположение, только сжатое/переносимое: кнопки, инпуты, карточки, простые ряды. |
| Отдельный вариант `viewport=desktop|mobile` | Композиция реально меняется: колонки складываются в стек, элементы скрываются/переставляются, меняется порядок (типично для Nav, Hero, секционных компонентов). |

Выбранный способ для каждого компонента фиксируется в плане библиотеки. Правило
по умолчанию: базовые компоненты — autolayout-поведение; секционные — отдельные варианты.

### Привязка к variables (`no-detached-values`)

Каждое значение в компоненте — цвет, шрифт, размер текста, отступ, радиус, тень —
привязано к variable/стилю из шага 1. «Отвязанное» значение допустимо только как
поимённо утверждённое исключение в worklog (раздел «Утверждённые исключения»).
Проверяется аудитом фазы 6 — но не откладывай на аудит: привязывай сразу.

### Autolayout

Autolayout обязателен на каждом фрейме компонента и каждом вложенном контейнере.
Абсолютное позиционирование — только для декоративных наложений, и каждый такой
случай фиксируется в worklog.

### Именование

Имена компонентов и props — английские (`Артефакты и их владельцы` в контракте):

- Компоненты: `Button/Primary`, `Button/Secondary`, `Card/Feature`, `Section/Hero`.
- Props: `size=sm|md|lg`, `state=default|hover|disabled`, `viewport=desktop|mobile`.
- Слои внутри компонента — тоже английские, осмысленные (`icon`, `label`, `media`),
  не `Frame 427`.

### Плейсхолдеры ассетов

Изображения внутри компонентов — плейсхолдеры по `placeholders-for-assets`:
нейтральный фрейм с привязанным фоном + подпись слота. Желаемый ассет описывается
в worklog (раздел «Ассеты-плейсхолдеры»).

## Чек-лист самопроверки перед гейтом 3

Прогнать полностью, результат записать в worklog как verification note фазы 4:

- [ ] Все коллекции variables созданы; имена 1:1 с ключами tokens.json; лишних нет.
- [ ] Режимы light/dark настроены, если tokens.json содержит обе темы; переключение проверено на 2–3 компонентах.
- [ ] Каждый компонент из плана библиотеки собран; ничего сверх плана не появилось.
- [ ] У каждого интерактивного компонента — варианты состояний; у используемых в нескольких размерах — prop `size`.
- [ ] У каждого компонента — мобильная версия или проверенное autolayout-поведение (сжать инстанс до мобильной ширины и посмотреть).
- [ ] Ни одного отвязанного значения при выборочной проверке (get_variable_defs по 3–5 компонентам); исключения — в worklog.
- [ ] Autolayout на всех фреймах; абсолютное позиционирование — только зафиксированные случаи.
- [ ] Имена компонентов, props и слоёв — английские, по конвенции.
- [ ] План библиотеки в worklog актуален (все дополнения по ходу внесены).
- [ ] Скриншоты компонентов сняты для предъявления человеку на гейте 3.

После чек-листа — остановка на гейте 3: предъявить библиотеку (скриншоты + ссылка
на файл), задать вопрос на утверждение, ждать явного «утверждаю» (`gates-are-blocking`).

## Уроки прогона yoga-school-demo (обязательные правила)

### Дефолтная белая заливка Figma

`figma.createFrame()` и `figma.createAutoLayout()` создают фрейм с БЕЛОЙ заливкой.
У каждого создаваемого контейнера заливку либо явно очищать (`fills = []`), либо
биндить к роли. Белые плашки на кремовых/тёмных фонах — типовой дефект, ловится
только рендером.

### Скриншот каждого компонента до гейта 3

Чек-лист «сжать инстанс и посмотреть» недостаточен. До гейта 3 снять скриншот
КАЖДОГО компонента в обоих вьюпортах (desktop и mobile варианты) — переполнения
текста и схлопывание FILL-в-hug ловятся только рендером. Заголовкам задавать
явную ширину переноса (textAutoResize=HEIGHT + FIXED width от ширины варианта);
FILL внутри hug-контейнера схлопывает текст в колонку.

### Раскладка холста библиотеки

Сеты компонентов на странице библиотеки раскладывать без наложений: вертикальный
стек с шагом ≥160px (позиции пересчитывать после каждого добавления, сеты растут).

### §specimen — образец для гейта 1

Specimen собирается в фазе 2 (до библиотеки!) на variables из tokens.json:
страница «01 Specimen» — палитра-свотчи, шкала типографики с образцами на языке
контента, кнопки/бейджи/инпуты, образец тёмной секции (инверсия режимом).
Тексты образцов — на языке контента проекта: это единственный способ поймать
отсутствие глифов до утверждения системы.

### Имена страниц Figma-файла проекта

Единая структура страниц: `01 Specimen` (образец системы, фаза 2),
`02 Components` (библиотека компонентов проекта, фаза 4), `03 Layouts`
(макеты страниц, фаза 5). Слово «Library» в имени страницы НЕ использовать —
оно зарезервировано за библиотекой паттернов комплекта (library/ в репо),
это разные вещи: библиотека паттернов переносится между проектами,
компоненты проекта — нет.

## Уроки прогона dk-sabi (обязательные правила)

### Респонсивная типографика через variable modes

Редукцию кегля между брейкпоинтами закреплять механизмом Figma **variable modes**, а не подменой
роли стиля на мобиле. Реализация:

1. Коллекция `breakpoint` с модами `Desktop` / `Mobile`.
2. На каждую роль типо-шкалы — FLOAT-переменная `type/size/<role>` (scope `FONT_SIZE`) со значениями
   desktop/mobile из `tokens.json.typeScale`.
3. `fontSize` каждого текст-стиля `DS/type/<role>` биндить к своей переменной:
   `textStyle.setBoundVariable('fontSize', v)` (API это поддерживает на уровне стиля).
4. `lineHeight` и `letterSpacing` держать в PERCENT — они масштабируются за `fontSize` сами,
   отдельные переменные под них не нужны.
5. Каждому фрейму-макету выставлять режим коллекции по его брейкпоинту:
   `frame.setExplicitVariableModeForCollection(col, modeId)` (desktop-фрейм → Desktop, mobile → Mobile).
   Фреймы без явного режима (Specimen, Components) резолвятся в дефолтный мод — регрессий нет.

Итог: **один набор текст-стилей**, размер следует за режимом фрейма; внутренний текст компонентов
внутри mobile-фрейма тоже уменьшается автоматически. Правило сборки: на мобиле роль стиля та же,
что на desktop (заголовок секции = `DS/type/h2` на обеих ширинах — размер меняет режим).

**Анти-паттерн:** собирать mobile-фрейм на desktop-стилях меньшей роли (`h3` вместо мобильного `h2`).
Размер иногда случайно совпадает, но система становится нечитаемой и неподдерживаемой — по имени стиля
не видно системной редукции.

### Лейблы компонентов (Eyebrow, Badge, chip) — перенос, а не авто-ширина

Текстовый лейбл внутри компонента с `textAutoResize='WIDTH_AND_HEIGHT'` (авто-ширина) НЕ переносится и
на узком БП вылезает за границу фрейма (поймано: Eyebrow с длинным надзаголовком «↗ ОСНОВАТЕЛЬ SABI ЦЕНТРА,
АВТОР „ПЯТОГО ВСАДНИКА"» — +111px за правый край mobile-390). Правило: у компонента с текст-лейблом,
который может быть длинным, root — `primaryAxisSizingMode='FIXED'` (не HUG по главной оси), label —
`textAutoResize='HEIGHT'` + `layoutSizingHorizontal='FILL'`; инстансы в макете ставить `layoutSizingHorizontal='FILL'`,
чтобы лейбл переносился в ширину контейнера. Это тот же класс, что «многострочные лейблы (consent 152-ФЗ)»
в граблях CLAUDE.md — распространяется на ВСЕ лейблы, которые бывают длинными, не только заведомо многострочные.

### Адаптив карты 2-кол → стек: `layoutWrap='WRAP'` вместо viewport-варианта

Когда карта на десктопе — два столбца (напр. «заголовок+мета | описание»), а на мобиле должна складываться
в один столбец, есть два пути: отдельный `viewport=desktop|mobile` вариант ИЛИ авто-поведение через wrap.
Для КАРТ (в отличие от секций) wrap чаще предпочтителен — **один компонент**, без дублирования варианта и без
переключения инстансов между вариантами. Рецепт (dk-sabi, Card/Seminar под референс Hollow /events):

1. Внутренний ряд-сплит: `layoutMode='HORIZONTAL'`, `layoutWrap='WRAP'`, `primaryAxisSizingMode='FIXED'`
   (ширина FILL от карты), `counterAxisSizingMode='AUTO'` (высота растёт при переносе), `counterAxisSpacing`
   задаёт зазор между перенесёнными строками.
2. Детям ряда — `layoutSizingHorizontal='FILL'` + **`minWidth`** (напр. левый столбец 240, правый 300).
   Порог переноса = сумма minW + gap: если внутренняя ширина карты ≥ (leftMin + gap + rightMin) — 2 колонки,
   иначе перенос в стек. Desktop-карта (широкая) → 2 кол; mobile-карта (узкая) → авто-стек.
3. Проверить рендером на обоих БП: на десктопе оба столбца в ряд, на мобиле — стек в 1 колонку.

Когда всё же viewport-вариант: если на мобиле меняется не только число колонок, а порядок/видимость слотов
или композиция (типично для Nav/Hero/секционных). Wrap решает только «колонки → стек тем же порядком».
Согласуется с таблицей «Десктоп + мобайл»: wrap = авто-поведение, годен для карт/рядов.
