# Content-doc: единый формат контента и структуры

Правила фазы 3. Выход фазы — `project/content-doc.md` по шаблону
`templates/content-doc.md`. Формат единый и обязательный независимо от того,
пришёл контент готовым или сгенерирован из брифа: фазы 4–6 читают контент-док
машинно-предсказуемо и не должны угадывать структуру.

Контент-док — источник правды для текстов и структуры страниц. В фазе 5 тексты
переносятся из него в макеты дословно (см. `docs/assembly-rules.md`), поэтому
всё, что не попало в контент-док, в макетах не появится.

## Два сценария входа

### Сценарий А — контент готов заранее

Человек передал контент (документ, черновик, тексты старого сайта — формат любой).
Агент:

1. Читает исходный контент целиком, ничего не выбрасывая.
2. Приводит его к формату этого дока: режет на страницы и секции, назначает id и типы,
   раскладывает тексты по полям. Тексты не переписывает — только структурирует.
   Замеченные проблемы (дубли, противоречия, отсутствующие куски) выносит в раздел
   «Открытые вопросы» контент-дока, а не чинит молча.
3. Валидирует полноту по критериям гейта 2 (ниже). Дыры (нет CTA, нет текста секции,
   непонятно назначение) — фиксирует как открытые вопросы к человеку.
4. Маппит каждую секцию на `reference-inventory.md`: есть ли в референсе аналогичная
   секция (предзаполнение каскада `composition-cascade` для фазы 5). Маппинг — часть
   вопроса на гейте 2.

Переписывать, «улучшать» или сокращать готовые тексты без запроса человека запрещено.
Предложения по улучшению — отдельным списком в открытых вопросах.

### Сценарий Б — контента нет, есть бриф

Агент генерирует структуру и тексты из `project/inputs.md` внутри фазы 3:

1. Из брифа извлечь: продукт/оффер, аудиторию, цель сайта (заявка, покупка,
   подписка...), тон, обязательные блоки, если человек их назвал.
2. Спроектировать карту страниц (для лендинга — одна) и для каждой страницы —
   последовательность секций под цель: какую задачу у посетителя решает каждая секция
   и почему стоит именно на этом месте. Ориентир по составу — секции референса из
   `reference-inventory.md` (что работает в этом жанре), но состав диктует бриф, а не референс.
3. Написать тексты всех секций: заголовки, подзаголовки, основной текст, пункты,
   CTA. Факты (цены, цифры, имена, сроки) — только из брифа; факта нет в брифе →
   плейсхолдер вида `[уточнить: стоимость тарифа Pro]` и открытый вопрос. Выдумывать
   факты запрещено.
4. Провалидировать полноту по критериям гейта 2 и предъявить человеку.

В обоих сценариях гейт 2 обязателен: человек утверждает структуру и контент
(`gates-are-blocking`). В сценарии А вопрос гейта включает подтверждение маппинга
на inventory; в сценарии Б человек фактически принимает и структуру, и тексты.

## Формат документа

Язык полей и текстов — русский; машинные идентификаторы (id страниц и секций,
типы секций) — английский kebab-case.

### 1. Карта страниц

Обязательна для многостраничников; для одностраничного лендинга — одна строка
с пометкой «одностраничник». Для каждой страницы:

- `id` страницы (kebab-case: `home`, `pricing`, `about`) — он же префикс имён
  фреймов в фазе 5 (`home/desktop-1440`);
- назначение страницы (одним предложением: зачем посетитель сюда попадает
  и что должен сделать);
- откуда на неё ведут ссылки (навигация, CTA других страниц).

### 2. Секции страницы

Для каждой страницы — упорядоченный список секций сверху вниз. Порядок в доке =
порядок в макете. Каждая секция описывается полным набором полей:

| Поле | Требование |
| --- | --- |
| `id` | kebab-case, уникален в пределах страницы (`hero`, `features-grid`, `pricing-table`). Используется в worklog и в именах слоёв Figma. |
| `type` | Тип секции из словаря: `hero`, `features`, `benefits`, `how-it-works`, `pricing`, `testimonials`, `logos`, `stats`, `team`, `gallery`, `faq`, `cta`, `contact-form`, `footer`, `header-nav`. Нет подходящего → свой тип kebab-case с пояснением в назначении. |
| Назначение | Какую задачу секция решает у посетителя (снять возражение X, показать выгоду Y, довести до действия Z). Одно-два предложения. По назначению секция матчится с inventory в фазе 5 — пустое или формальное назначение ломает каскад. |
| Контент | Заголовок; подзаголовок (если есть); основной текст; пункты/элементы списка (для features, faq, pricing — каждый пункт со своим заголовком и текстом); CTA: точный текст кнопки/ссылки + куда ведёт (страница/якорь/URL). Тексты — финальные формулировки, не описания («заголовок про скорость» — не контент). |
| Ассеты | Для каждого изображения секции — описание по правилу `placeholders-for-assets`: сюжет, стиль, формат/ориентация (например: «фото команды в офисе, светлое, горизонтальное 3:2»). Нет ассетов — явно `нет`. |
| Мобильный приоритет | Что происходит с секцией на мобильном: что сворачивается (аккордеон, карусель), что скрывается, что меняет порядок. Секция без изменений — явно `без изменений`. |

## Чего в контент-доке НЕТ

Контент-док описывает структуру и смысл, а не внешний вид. Запрещено указывать:
цвета, шрифты, размеры, отступы, радиусы, тени, конкретные компоненты библиотеки
и раскладку («три колонки», «слева картинка») — композиция определяется в фазе 5
по каскаду `composition-cascade`, визуальные значения — только из tokens.json
(`reference-source-of-truth`). Обнаружил визуальные указания в готовом контенте
(сценарий А) — вынеси их в открытые вопросы как пожелания человека, из полей секций убери.

Единственное допустимое «структурное» указание — порядок секций и мобильный приоритет:
это смысловые решения, а не визуальные.

## Связь с фазой 5

Каждая секция контент-дока при переходе в фазу 5 обязана получить источник композиции
по `composition-cascade` (референс → `library/skeletons/` → invented). Поля `type`
и «Назначение» — ключи матчинга с `reference-inventory.md`, поэтому они обязательны
и содержательны для каждой секции без исключений. Секция, которую невозможно
сматчить ни по типу, ни по назначению, почти гарантированно уйдёт в `invented` —
это допустимо, но должно быть осознанным, а не следствием пустых полей.

## Критерии полноты (гейт 2)

Контент-док готов к предъявлению на гейте 2, когда всё нижеследующее истинно:

- [ ] Карта страниц есть; у каждой страницы — id, назначение, входящие ссылки
      (или зафиксировано: одностраничник).
- [ ] Каждая страница разбита на секции, порядок явный; у каждой секции заполнены
      все шесть полей (id, type, назначение, контент, ассеты, мобильный приоритет) —
      без пустых и без «см. выше».
- [ ] id страниц и секций — kebab-case, уникальны, на английском.
- [ ] Все тексты — финальные формулировки; описаний-заглушек вместо текста нет.
      Неизвестные факты оформлены как `[уточнить: ...]` и продублированы
      в открытых вопросах.
- [ ] Каждый CTA имеет точный текст и адрес назначения; ссылки между страницами
      ведут на существующие id из карты страниц.
- [ ] Каждый ассет описан по `placeholders-for-assets` (сюжет, стиль, формат)
      либо у секции стоит явное `нет`.
- [ ] Визуальных решений в доке нет (проверено по списку запретов выше).
- [ ] Маппинг секций на reference-inventory выполнен: для каждой секции отмечено
      «есть аналог в референсе: <id из inventory>» или «аналога нет».
- [ ] Открытые вопросы собраны в отдельный раздел; блокирующие (без ответа нельзя
      собирать макет) помечены.
- [ ] В worklog — decision trail фазы 3: сценарий (А/Б), ключевые решения по структуре,
      отвергнутые альтернативы (`worklog-required`).

Агент предъявляет контент-док + маппинг + открытые вопросы и ждёт явного «утверждаю».
Ответы человека на открытые вопросы вносятся в док до фиксации гейта.
